# Requirements: reliable webhook delivery

> Manual, source-faithful example — not generated by Kiro.

## Introduction

This spec defines reliable outbound webhook delivery for a multi-tenant TypeScript SaaS API. It covers signed requests, duplicate protection, retries, dead-letter handling, manual replay, audit history, isolation, observability, and acceptance tests.

## Requirements

### 1. Signed delivery

**User story:** As a webhook consumer, I want to verify each request so that I can reject forged or altered events.

#### Acceptance criteria

1. WHEN the service sends a webhook THEN it SHALL include a signature and the data needed to verify that signature.
2. WHEN a consumer verifies an unmodified request with the matching secret THEN verification SHALL succeed.
3. WHEN the payload, signature, or verification secret is wrong THEN verification SHALL fail.

### 2. Idempotent delivery

**User story:** As a webhook consumer, I want a stable event identity so that retries do not create duplicate effects.

#### Acceptance criteria

1. WHEN the service retries an event THEN it SHALL reuse the event's stable identifier.
2. WHEN the service records delivery state THEN it SHALL distinguish the event from each delivery attempt.
3. IF concurrent workers claim the same pending delivery THEN at most one worker SHALL send that attempt.

### 3. Bounded retries and dead-letter handling

**User story:** As an operator, I want failed requests retried and then quarantined so that temporary failures recover without retrying forever.

#### Acceptance criteria

1. WHEN a retryable delivery fails THEN the service SHALL schedule another attempt with exponential backoff and jitter.
2. WHEN a delivery succeeds THEN the service SHALL stop retrying it.
3. WHEN a delivery exhausts its retry policy THEN the service SHALL move it to a dead-letter state.
4. WHEN a failure is not retryable THEN the service SHALL record the outcome without another automatic attempt.

### 4. Manual replay and audit history

**User story:** As an authorized operator, I want to inspect and replay failed deliveries so that I can recover after fixing a consumer endpoint.

#### Acceptance criteria

1. WHEN an authorized operator requests a replay THEN the service SHALL create a new, auditable delivery attempt.
2. WHEN any attempt completes THEN the audit log SHALL record its tenant, event, endpoint, time, outcome, and response summary.
3. WHEN an operator views delivery history THEN the service SHALL return only records that operator may access.

### 5. Tenant isolation

**User story:** As a tenant, I want my webhook configuration and history isolated so that another tenant cannot view or change it.

#### Acceptance criteria

1. WHEN a request reads or changes endpoints, deliveries, dead letters, replays, or audit records THEN it SHALL apply the authenticated tenant boundary.
2. IF an identifier belongs to another tenant THEN the service SHALL not reveal that resource.

### 6. Observability and acceptance tests

**User story:** As an operator, I want delivery signals and executable checks so that I can detect failures and verify the system's guarantees.

#### Acceptance criteria

1. WHEN the service processes deliveries THEN it SHALL expose metrics for attempts, successes, failures, retries, dead letters, and latency.
2. WHEN an attempt is traced or logged THEN its records SHALL carry tenant-safe correlation identifiers.
3. WHEN the acceptance suite runs THEN it SHALL cover signing, idempotency, retry timing and jitter bounds, dead-letter transition, manual replay, audit history, tenant isolation, and observable signals.

## Open requirements questions

- Which signature algorithm and rotation policy should the service use?
- Which status codes or network failures are retryable?
- How many attempts and how much elapsed time form the retry limit?
- How long should payloads, response summaries, audit entries, and dead letters remain available?
- Does manual replay need an API only, or also an operator UI?
