# Design: reliable webhook delivery

> Manual, source-faithful example — not generated by Kiro.

## Overview

Use a durable delivery record as the boundary between the SaaS API and outbound HTTP work. The API records an event and one delivery per subscribed endpoint. Workers claim due deliveries, sign the exact outbound bytes, send them, and append an immutable attempt record. A scheduler makes retryable deliveries eligible again. Exhausted deliveries enter a dead-letter state. An authorized replay action creates a new attempt trail without erasing the original failure.

## Architecture

```text
Application transaction
  -> event + delivery records
  -> due-delivery worker
  -> signed HTTP request
  -> attempt record
       -> success
       -> scheduled retry (backoff + jitter)
       -> dead letter

Operator API -> audit query / manual replay
Metrics + logs + traces <- worker, scheduler, operator API
```

## Components and interfaces

### Event writer

- Accepts a tenant-scoped domain event.
- Stores the canonical event identity and payload.
- Creates delivery records for eligible tenant endpoints in the same durable boundary where practical.

### Delivery worker

- Atomically claims a due delivery.
- Builds one canonical byte sequence and signs that sequence.
- Sends the request with event, attempt, timestamp, and signature metadata.
- Classifies the response as success, retryable failure, or terminal failure.
- Appends an attempt record before moving delivery state.

### Retry scheduler

- Selects retryable deliveries whose next-attempt time has passed.
- Uses exponential delay capped by policy and perturbed by jitter.
- Prevents a thundering herd after a broad consumer outage.

### Dead-letter and replay service

- Lists dead-letter records within the authenticated tenant.
- Authorizes and records replay requests.
- Starts a new delivery cycle linked to the original event and failure trail.

### Audit query service

- Returns a chronological attempt history.
- Redacts secrets and bounds response-body capture.
- Filters by tenant at the data-access boundary.

## Data model

| Entity | Purpose | Key relations |
| --- | --- | --- |
| Tenant | Isolation boundary | owns endpoints, events, deliveries |
| Webhook endpoint | Target URL and signing-secret reference | belongs to tenant |
| Event | Stable id, type, payload, created time | belongs to tenant |
| Delivery | State for one event-to-endpoint path | links event and endpoint |
| Delivery attempt | Immutable send outcome | belongs to delivery |
| Dead-letter record | Exhausted or terminal failure | points to delivery |
| Replay request | Actor, reason, time, result | points to original delivery |
| Audit entry | Operator and delivery actions | belongs to tenant |

## Correctness properties

- A retry preserves the event identifier but receives its own attempt identifier.
- Claiming work is atomic; two workers cannot both own the same attempt.
- A success is terminal for that delivery cycle.
- Replay adds history and never rewrites the failed attempts.
- Every query and mutation carries a tenant scope to storage.
- The service never logs a signing secret or unbounded response body.

## Error handling

Classify transport errors, timeouts, and configured response classes before scheduling another attempt. Persist the classification and bounded diagnostic data. If the worker crashes after sending but before recording the response, recover through the same event identity and consumer-facing idempotency contract; do not promise exactly-once delivery.

## Testing strategy

- Unit tests for canonical signing bytes, signature verification, delay calculation, jitter bounds, and response classification.
- Storage tests for atomic claims, terminal transitions, concurrent workers, and tenant filters.
- HTTP integration tests with a controllable receiver for success, timeout, malformed response, retry, and replay.
- Acceptance tests mapped one-to-one to the requirements file.
- Fault tests for process death between claim, send, and result persistence.

## Unresolved design choices

The queue, database, HTTP framework, signature algorithm, retry limits, retention policy, cloud provider, and presence of an operator UI remain open. A real implementation should resolve them with recorded rationale before work begins.
